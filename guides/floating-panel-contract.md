# FloatingPanel shared contract

## Default responsive support

The shared panel and toolbar layouts support two default device profiles. The 16-inch MacBook Pro uses a full-screen 1728 × 1117 CSS-pixel viewport at 2× with a fine pointer and keyboard. The portrait iPhone 13 uses a 390 × 844 CSS-pixel screen at 3×, with 390 × 664 available when browser controls are visible. Its coarse-pointer toolbar controls have a 44 CSS-pixel minimum hit area.

Consumers use the shared styles for layout and import `supportedResponsiveTargets` from `agentic-design-system/annotation-targets` in their existing browser checks. To add a supported device, extend the owner profile list, its type declaration and its acceptance check, then update the consumer pin. The application responds to the available space and pointer capabilities.

## Common action icons

`site/icons.json` owns the semantic `panelControls` map for `search`, `pin`, `apply`, `reset`, `minimize`, `restore`, and `close`, including each role’s canonical icon and accessible label. Consumers use those roles through their shared UI adapter; they do not define local glyph aliases, labels, or copy icon paths. Panel controls use the same neutral labels across products (`Search`, `Pin`, `Apply`, `Reset`, `Minimize panel`, `Restore panel`, and `Close`). Panel restoration uses the maximize icon; history restoration remains a distinct history action and is never mapped to the panel `restore` role. Consumer governance documents reference this map; they do not restate role-to-glyph or role-to-label pairs as a second authority.

Generic intent, focus, ring, status, surface-wash and row-selection presentation is owned by `site/ui-intent-palette.json` (`agentic-design-system/ui-intent-palette/v1`). Consumers derive their class strings and paint values from the pinned central bytes; locally authored equivalent tables or overrides are forbidden. Domain-specific visualization semantics remain with their product owners unless this contract explicitly absorbs them.

Agentic Design System owns the shared MainPanel, FloatingPanel, and BottomPanel presentation plus Editor Workspace layout. The profile in `site/tokens/shared-ui-profile.json` owns panel width, bottom height, gap, surface colors, border, radius, and the single toolbar shadow token. The central stylesheet is `site/floating-panel.css`; it provides `.agentic-panel-main`, `.agentic-panel-bottom`, `.agentic-panel-main-dock`, `.agentic-panel-bottom-dock`, `.agentic-editor-workspace`, and `.agentic-editor-workspace-stage`. Design System owns the `.agentic-base-floating-panel` selector definitions as part of its panel DOM contract; Base does not own a parallel adapter or compatibility layer. Icons reuse the existing shared `.agentic-icon` class and its centrally owned size and stroke tokens.

Expanded and minimized panels use the same shared toolbar row height, border, radius, shadow, and icon stroke. Minimize changes the panel content and the panel's documented size behavior only; it does not switch to a second chrome profile. A minimized one-row header removes its content inset and inner divider so the panel's outer border remains the single toolbar-matching edge. Expanded MainPanel, FloatingPanel, and BottomPanel tabs all show the selected label and reveal other labels on hover or keyboard focus. Minimized panel headers remain icon-only while retaining accessible names.

Expanded MainPanel and viewport FloatingPanel dimensions come from the same shared viewport profile. Opening, closing, or switching a different panel does not resize either panel; content scrolls inside the fixed shared shape. The shell does not observe sibling panels or make space by shrinking another panel. Only viewport size and safe-area limits may constrain the shared profile dimensions.

Agentic Design System owns the semantic panel-control map, icon rendering runtime, labels, visual treatment, control order, expanded/minimized visibility, DOM group rendering, React and native adapters, lifecycle mechanics, and shared MainPanel, FloatingPanel, and BottomPanel placement rules. `site/toolbar-icons.js` is the one control runtime; consumers use its immutable projection and do not implement a second group renderer. All products, including Base, import the pinned Design System adapters directly and bind their own callbacks and product state. There is no Base-owned bridge, forwarding adapter, or re-export path. Products may choose only the documented placement modes. Consumers must not define panel token values, panel variants, role maps, control order, control visibility rules, group rendering, or local radius, shadow, background, border, header, spacing, or responsive sizing overrides. The shared token profile, semantic map, runtime, adapters, and shell stylesheet are the only source for these values.

`FloatingPanelPanelStyle` accepts positioning and sizing only. The shell root accepts one `rootPlacement` value: `flow`, `dock`, or `viewport-overlay`; the shared adapter maps it to shared placement behavior. A `viewport-overlay` places the panel below the shared toolbar row and edge gap, respects safe-area insets, and sizes it within the remaining viewport height. When host chrome consumes additional space, the host supplies its total top inset through `viewportBlockStartOffset` (or `--agentic-floating-panel-block-start-offset` for native DOM); the shared rule uses that same inset for placement and available height. Consumers do not calculate a second panel height or override the panel's block size. They reuse this placement value when restoring a user-dragged position. Shell, tabs, and controls do not accept consumer classes, visual CSS overrides, or icon-size and stroke-width props. Tab selection comes only from the parent `activeKey`; keyboard navigation and selected-tab scrolling are shared behaviors. Expanded and minimized panel tabs use the same icon-and-label behavior: the selected label remains visible, and other labels appear on hover or keyboard focus. The shared tab rail keeps the selected or interacted-with tab in view. Icons receive the shared `.agentic-icon` class, which owns dimensions and stroke. Panel headers, tabs, and close controls share `--agentic-toolbar-height` for their block size (38px desktop, 54px on touch or narrow viewports); tabs keep `--agentic-control-height` as the minimum inline size for compact use. Consumers do not add panel-specific touch-size variants.

Consumer projections bind the exact Design System revision and file digests. Rollback restores those exact prior files and pins together. This source contract does not select package publication, deployment, or production activation.

For a native browser, import `mountFloatingPanel` from `agentic-design-system/floating-panel`. Pass the opening button, a hidden container with a unique ID, and a label. Each direct child supplies a stable `data-panel-tab` key, `data-panel-label`, optional registry `data-panel-icon`, and the product content. The component builds the shell on first open, handles tab navigation and provides the shared Close control. A host that edits text can supply `returnFocus` to restore its editor selection.

### Shared navigation across routes

Keep the product’s destinations and Skills & Commands trigger in one toolbar template or component. Each participating route uses that owner, the same application base stylesheet, and the Design System toolbar styles. Mark the current destination with `aria-current="page"`. Use the canonical `agentic-design-system/toolbar.css` export for a standalone toolbar or `agentic-design-system/panels.css` for the complete surface. Offline builds may seal the exact pinned source bytes. Test navigation and the panel from each route, including narrow and offline layouts.

### Skills & Commands

Import the tab metadata and catalog header from `agentic-design-system/skills-commands` and its styles from `agentic-design-system/skills-commands.css`. The header owns prefix selection, Subject/Verb/Object grouping, search and bulk disclosure. Interactive hosts supply rows, disclosure state, catalog provenance and activation handlers. Use the shared catalog, body, list, row, title and metadata classes for their layout. A read-only host can use `mountSkillsCommandsReference` for the entire tab. Both adapters work with local data and preserve product authorization boundaries.

## Tab content

Use `agentic-panel-tab-layout` for the full-height content surface. Place `PanelTabHeader` and `agentic-panel-tab-body` as siblings. The heading, optional subtitle and wrapping actions stay visible while the body scrolls. Put projections and collapsible sections inside that body. The native Skills & Commands catalog shares these styles. Plain DOM consumers can import `agentic-design-system/panel-tab-layout.css` and use the same classes.

For a split editor or transport that manages its own viewport, put its single root inside the tab body and set `data-agentic-tab-viewport="true"` on the body. The editor receives the available height while the tab retains the shared insets.

Native consumers can load `agentic-design-system/panels.css` for the complete MainPanel, FloatingPanel and BottomPanel styles. Offline bundles resolve its imports in order from the same pinned revision. For expandable groups, use `createPanelSectionSummary(document, label, level)` inside native `details[data-agentic-section]`, or the React `CollapsibleSection`. Both use the same heading row and disclosure chevron. Product content, persisted state and placement inputs stay with the host.

Native hosts that route external launchers to tabs can call `open(key, { focus })`, `select(key)` or `close(false)` and observe `onChange({ open, key })`. The shell owns keyboard navigation, selection and controls. `activeKey` and `isOpen` on the returned controller expose current state; each visible change produces one notification. Host content can be populated before first open.
